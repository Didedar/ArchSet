# Совместная работа над раскопом (Collaborative Dig Sites)

**Дата:** 2026-08-02
**Статус:** дизайн согласован, план реализации не написан

## Задача

Два археолога должны совместно вести один раскоп: видеть записи друг друга,
дополнять их и не терять свою работу — при том что основная часть полевого дня
проходит **без сети**.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Режим работы | Асинхронный. Слияние при появлении сети. Живого соредактирования нет. |
| Единица общего доступа | **Папка** = раскоп/экспедиция. Всё внутри становится общим. |
| Конфликт правок одной заметки | Обе версии сохраняются целиком. Текст заметки не теряется никогда. |
| Роли участников | Нет. Все приглашённые — редакторы. Владелец отличается только правом приглашать/исключать. |
| Файлы фото | **Не входят в v1.** Метаданные артефактов синхронизируются, файлы снимков остаются на устройстве автора. |

## Не входит в v1

Файлы фотографий, живое соредактирование, роли и права доступа, сборка мусора
в хранилище, приглашение без сети.

## 0. Предусловие: офлайн-сессия (баг, который надо починить первым)

Без этого фикса вся фича нерабочая, поэтому он — отдельный первый шаг, а не
часть совместной работы.

### Что сломано сейчас

`AuthService.loadStoredUser()` (`lib/data/services/auth_service.dart:285`) при
недоступном сервере возвращает `null`:

```dart
case _MeUnreachable():
  return null; // keep token; unverified, not disproven
```

Дальше `SessionCubit.bootstrap()` трактует `null` как отсутствие пользователя и
выдаёт `SessionGuest`, что обнуляет `CurrentOwnerHolder`. А
`NotesRepository._ownerFilter` (`lib/data/repository/notes_repository.dart:23`)
при `owner == null` показывает только строки с `ownerKey IS NULL`.

**Итог: залогиненный пользователь, запустивший приложение без сети, видит
пустой дневник.** Данные целы в SQLite, но отфильтрованы. Это ломает приложение
уже сегодня, независимо от совместной работы.

### Исправление

Приложению нужно различать три состояния, а не два:

| Состояние | Значение | `ownerKey` |
|---|---|---|
| Гость | Сознательно без аккаунта | `null` |
| Аккаунт, сеть есть | Личность подтверждена сервером | `<user id>` |
| Аккаунт, сети нет | Личность известна, не подтверждена | `<user id>` |

Правило: **«не смог проверить» ≠ «проверил и отказано»**.

- `_MeUnreachable` → вернуть закэшированного пользователя из secure storage.
  `user_id` и `user_email` там уже пишутся `_persistUser`
  (`lib/data/services/auth_service.dart:345`). Токен не трогать.
- `_MeRejected` → рефреш → неудача → закрыться намертво. **Без изменений.**

Fail open при недоступности, fail closed при отказе.

Срока годности у офлайн-сессии нет: экспедиция может быть в поле неделями.
Проверка происходит при каждом успешном контакте с сервером.

Новой уязвимости это не создаёт: данные и так лежат на устройстве, а токен
офлайн бесполезен.

`AuthService.notifySessionExpired()` дёргается только на невосстановимом 401,
то есть на реальном отказе сервера — эта ветка корректна и не меняется.

## 1. Модель данных

### Бэкенд

Новая таблица:

```
folder_members(folder_id, user_id, joined_at)
  PK (folder_id, user_id)
  FK folder_id -> folders.id ON DELETE CASCADE
  FK user_id   -> users.id   ON DELETE CASCADE
```

Единое правило доступа во всех запросах:

> пользователь имеет доступ к папке F, если `F.user_id == me`
> **или** существует `folder_members(F.id, me)`

Заметки, артефакты и комментарии наследуют доступ через свою папку.
Заметки с `folder_id IS NULL` не расшариваются никогда — это личные черновики.

Колонка `revision INTEGER NOT NULL DEFAULT 1` добавляется в `notes`, `folders`,
`artifacts`, `artifact_comments`. Назначается и увеличивается **только
сервером**.

### Клиент

**`ownerKey` не меняет смысла.** Он остаётся ответом на вопрос «реплика какого
локального аккаунта эта строка». Строку из общей папки, скачанную Иваном,
помечаем `ownerKey = ivan`; копию Марии — `ownerKey = maria`. Существующий
фильтр чтения и недавний фикс утечки между аккаунтами продолжают работать без
изменений.

Кто **написал** строку — новая отдельная колонка `authorId`. Используется только
для отображения авторства и подписи конфликтных копий.

Разделение «чья это реплика» (`ownerKey`) и «кто автор» (`authorId`) — ключевое
решение: оно позволяет добавить совместную работу, не трогая механизм
безопасности.

### Миграция Drift v9 → v10

| Таблица | Добавляется |
|---|---|
| `Folders` | `isShared` (bool, default false), `ownerAuthorId` (text?), `baseRevision` (int?) |
| `Notes` | `authorId` (text?), `baseRevision` (int?) |
| `ImageMetadata` | `authorId` (text?), `baseRevision` (int?) |
| `ArtifactComments` | `authorId` (text?), `baseRevision` (int?) |

Существующие строки: `authorId = ownerKey`, `baseRevision = null`,
`isShared = false`. Все текущие записи становятся личными записями своего
владельца — чем они и являются.

## 2. Протокол синхронизации

### Порядок: сначала push, потом pull

Это не деталь реализации, а требование корректности: конфликты обнаруживаются
только при отправке. Обратный порядок теряет их молча.

### Обнаружение конфликта — по ревизиям, не по времени

Клиент хранит `baseRevision` — ревизию, которую последней получил с сервера.
При локальной правке `baseRevision` **не меняется**: он помнит, от какой
серверной версии человек отталкивался.

При отправке клиент присылает строку вместе с её `baseRevision`. Сервер:

| Условие | Действие |
|---|---|
| Строки нет | Создать, `revision = 1` |
| `server.revision == baseRevision` | Принять, `revision++` |
| `server.revision != baseRevision` | Отказ `409`, вернуть свою версию |

**Почему ревизии, а не сравнение `updatedAt`.** Телефоны, неделю пробывшие в
поле без сети, расходятся по часам. В коде уже есть костыль против этого —
`bufferTime = lastSyncAt - 5 секунд` в синхронизации артефактов
(`lib/data/services/sync_service.dart:347`). Сравнение времени тихо выберет не
того победителя. Серверный счётчик к рассинхрону часов невосприимчив.

`baseRevision = null` означает «строка ещё ни разу не была на сервере» — новая
локальная запись или свежий форк. Сервер трактует такую отправку как создание.

### Обработка ответа клиентом

- **Принято** → `baseRevision = новая ревизия`, `pendingSync = false`.
- **Отказ `409`** → версия сервера записывается под исходным `id`. Что
  происходит с локальной правкой — **решает клиент, по типу сущности** (ниже).
  Сервер одинаково возвращает `409` для всех типов и политику не знает.

### Политика конфликта — по типам сущностей

Разные сущности требуют разного, и это осознанное решение. **Оно означает, что
обещание «ничего не теряется» относится к тексту заметок**; для папок и
артефактов проигравшая правка отбрасывается сознательно, по причинам ниже.

- **Заметки — форк.** Новый `id`, заголовок `«<название> (версия <автор>,
  <время>)»`, `authorId` = тот, кто форкает (то есть проигравший в гонке),
  `pendingSync = true`, `baseRevision = null`. Уезжает как новая заметка, обе
  стороны видят обе.
- **Папки — LWW по метаданным** (`name`, `color`), локальная правка
  отбрасывается. Форкать раскоп бессмысленно: получилось бы два раскопа.
  Потерянное переименование восстанавливается руками за пять секунд.
- **Артефакты — LWW**, локальная правка отбрасывается. Форк дублировал бы
  физическую находку на карте, то есть приводил бы к двойному учёту — для
  археологии это хуже, чем потеря правки текста анализа. Артефакты к тому же
  почти всегда пишутся один раз при съёмке и потом не меняются.
- **Комментарии — конфликтов нет by design.** Каждый комментарий — отдельная
  строка со своим автором; они только добавляются.

### Что уже есть и переиспользуется

Снятие `pendingSync` только с подтверждённых строк, с проверкой по
`id + updatedAt`, чтобы правка, сделанная во время отправки, не потеряла флаг
(`lib/data/services/sync_service.dart:313`).

## 3. Приглашение

Требует сети — это неизбежно, нельзя договориться с сервером о новом участнике,
не связавшись с сервером. Делается один раз в лагере.

- `POST /folders/{id}/members` — тело `{email}`. Только владелец. Если
  пользователя с такой почтой нет — `404` с внятным текстом.
- `DELETE /folders/{id}/members/{user_id}` — только владелец.

Приглашённый получает папку и всё её содержимое при ближайшей синхронизации.

**Гость участником быть не может** — членство требует `user_id`. В интерфейсе
раздел виден, но заперт, с кнопкой входа. Путь «гость → участник» уже
существует: `GuestClaimCoordinator` при регистрации присваивает локальные
гостевые записи новому аккаунту, ничего не теряя.

## 4. Крайние случаи

**Доступ отозван, пока участник в поле.** Push вернёт `403`. Его работу **не
удаляем**: строки отцепляются от папки (`folderId = null`) и остаются личными
заметками с пометкой «доступ к раскопу закрыт». Удалять чужой текст из-за
админского действия недопустимо.

**Правка заметки, которую другой удалил.** Удаление — tombstone (`isDeleted`),
не физическое стирание. Правка живой строки против удалённой — обычный конфликт
ревизий: версия правившего форкается и выживает.

**Обрыв синхронизации посередине.** `pendingSync` снимается только с
подтверждённых строк (см. выше). Неотправленное остаётся грязным.

**Выход из аккаунта офлайн с несинхронизированными правками.** Офлайн-выход в
приложении работает (коммит `fix: offline sign-out no longer hangs`), и работа
останется на устройстве невидимой, пока человек не войдёт тем же аккаунтом.
Показываем предупреждение — не запрет:

> «12 записей ещё не отправлены в раскоп «Раскоп 3». Если выйти сейчас, они
> останутся на этом устройстве и попадут к коллегам только после того, как вы
> снова войдёте в этот аккаунт.»

**Refresh-токен протух за время в поле.** Сервер отказывает → честный разлогин →
нужен пароль. Несинхронизированные правки при этом сохраняются: разлогин чистит
сессию, а не данные. Это подтверждается тестом, а не доверием к названию метода.

**Расхождение часов между устройствами.** На слияние не влияет: решение
принимается по серверному счётчику. Время нужно только для подписи под форком.

## 5. Интерфейс

- **Список папок** — бейдж «Общий» и участники.
- **Экран раскопа → «Участники»** — список, «Пригласить» (по email),
  «Исключить» (только владелец).
- **Гость** — раздел заперт: «Нужен аккаунт» + кнопка входа.
- **Чужая заметка** — подпись «автор: Мария».
- **Конфликтная копия** — плашка сверху: «Это ваша версия. Коллега правил ту же
  запись» со ссылкой на вторую. Без неё две похожие заметки читаются как баг.
- **Артефакт коллеги** — на месте снимка плашка «Фото на устройстве автора», не
  битая картинка.
- **Выход офлайн с грязными строками** — предупреждение выше.

## 6. Тестирование

Проверяется тестами, а не рассуждением:

1. **Доступ.** Не-участник не получает чужую папку ни через `/sync`, ни через
   прямые ручки. Тот же класс, что закрытая утечка между аккаунтами;
   проверяется на сервере.
2. **Офлайн-сессия.** `_MeUnreachable` → пользователь остаётся собой, дневник не
   пустой. Регрессия на баг из раздела 0.
3. **Конфликт заметок.** Два клиента правят одну заметку от одной базовой
   ревизии → обе версии живы, ни одна не перезаписана.
4. **Порядок push→pull.** Обратный порядок теряет конфликты молча — тест должен
   ловить именно это.
5. **Отзыв доступа не удаляет чужую работу.**
6. **Разлогин не трогает таблицы заметок.**
7. **Миграция v9 → v10** на непустой базе: `authorId` проставлен из `ownerKey`,
   строки не потеряны.

Запуск: `flutter test --concurrency=1`. Суита нестабильна:
`audio_bloc_test.dart` → «AudioSegmentDeleted recalculates start positions»
падает примерно 1 запуск из 3 **на неизменённом дереве**. Расхождение в один
этот тест — известная флакость, а не регрессия.
